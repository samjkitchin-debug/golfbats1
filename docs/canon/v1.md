## 1. Purpose and Product Stance

DayForeIt exists to remove friction until only the game remains.

This is not a dashboard product. This is not a CRUD app. This is not a feed.

DayForeIt is an **instrument** for coordinating and playing golf with other people.

### Beta ladder

Beta sequencing is governed by [`beta-roadmap.md`](./beta-roadmap.md). Architectural changes must remain consistent with that ladder to prevent drift.

## 2. Information Architecture and Navigation Contract

### Canonical Hamburger Navigation

All authenticated users see:
- **Home** → `/`
- **Trips** → `/trips`
- **Members** → `/members`
- **Results** → `/results`
- **Me** → `/me`

### Admin Mode

Admin is a **capability**, not a separate product or navigation item.

- Admin capabilities on the Members page are derived from **per-group role** (admin) only. There is no "admin mode" toggle; approval and role controls appear automatically when viewing a group where the user is an admin.
- "All groups" is read-only. If there are pending approvals in any group where the user is admin, a banner with a "Review" CTA jumps to the first admin group that has pending.
- Admin tools are contextual, not global. Admin surfaces feel like a quiet workshop, not a separate app.

### Personal golf surfaces

Personal golf artefacts (e.g. a member’s rounds, handicap, and progression) are conceptually part of the Clubhouse domain, even when viewed in a single-player context. These surfaces represent golf activity, not identity or account management.

The “My golf” entry point currently appears on the Me page as early scaffolding. This is a temporary placement for v1 and does not reflect its long-term ownership. In future iterations, personal golf views should live within Clubhouse navigation rather than the Me/Profile surface.

- Me page is reserved for identity, profile, and account-level settings.
- No implementation or migration is implied in v1; this is an intent lock only.

## 3. Design Manifesto

### Core Philosophy

### Simple is hard

"Simple is hard" is a core Day Fore It philosophy. Simplicity is achieved by removing thought and decisions, not by hiding complexity. If the user has to think, we failed.

Performance and responsiveness are part of simplicity. Instant is better than clever. We choose inevitability over optionality.

This principle applies across the app, from trip coordination to GameDay scoring. Every interaction should feel inevitable and thoughtless.

**Simple is hard.** Simplicity is decisional reduction, not visual minimalism. Every screen answers only the most important questions for that moment.

**Mode-driven, not page-driven.** The app is organised around modes (Selection, Execution, Live Instrument), not destinations.

**Instrument, not dashboard.** Instruments use continuous surfaces, state-first layout, direct manipulation, reading before acting. Avoid card stacks, multiple CTAs, dashboard patterns.

**State before data.** Golfers think in birdie/par/bogey, not tables or raw numbers. Relative-to-par is first-class.

**Reading comes before acting.** Context first, recognition second, action last. Primary actions are quiet.

**Surfaces are affordances.** The surface itself is tappable. "View details" is not a concept. Users lean in, they don't navigate.

**Direct manipulation over data entry.** During execution: no dropdowns, no +/- buttons, no modal decision trees. Interactions feel physical: tap, slide, swipe.

**Personal-first, group-aware.** The user's state is gently emphasised. The group context is always visible. No mid-round leaderboards, no judgement, no pressure.

**Flow over confirmation.** Fewer confirmations, more momentum, clear acknowledgement, automatic progression.

### Language and Tone

DayForeIt is a coordination tool, not a social network.

- Avoid social-media language ("post", "share", "publish")
- Use neutral, calm coordination language ("Create", "Set up", "All set", "View details")
- Copy assumes small groups organising together, not performing for an audience
- UK English, sentence case

### Typography

Typography is **neutral by design**. DayForeIt uses **Inter** to prioritise clarity, hierarchy, and measurement over visual expression.

**Inter is mandatory.** Inter is the only font allowed. No fallbacks to system fonts (`font-sans` is forbidden). All text must use Inter via the `--font-inter` CSS variable. Violations are build-blocking (VISUAL-02 audit).

Unboxed text must follow the page rail. Primary instrument surfaces use a single consistent horizontal rail. All unboxed content on a page must share the same horizontal alignment.

### Visual System Lockdown

**Palette colors are forbidden.** Tailwind default palette colors (`blue-*`, `slate-*`, `gray-*`, `zinc-*`, `neutral-*`) must not be used. Only semantic color tokens are allowed:
- Surfaces: `bg-surface`, `bg-surface-2`, `bg-background`
- Text: `text-foreground`, `text-muted`
- Borders: `border-border`
- Brand: `bg-primary`, `text-primary`, `bg-anticipation`, `text-anticipation`
- Danger: `bg-danger`, `text-danger`
- Warning: `bg-warning`, `text-warning`

Violations are build-blocking (VISUAL-01 audit). See `src/app/globals.css` for the complete semantic token system.

### Instrument behaviour

Instrument behaviour is **phase-agnostic**. Behaviour (done, status, density, interactivity) is determined exclusively by `instrument.kind` via `resolveInstrumentRenderState`. Phase controls **visibility** only (which instruments are shown); it must not affect how an instrument renders or behaves.

- **status_control:** never done, never compact, always interactive; `compactWhenDone` is ignored.
- **job:** `isDone` and `compactWhenDone` define completion and density.

The renderer consumes only the resolved state. Violations are build-blocking (INSTRUMENT-01 audit).

### Instrument phase visibility

Instruments declare **phase visibility** in the registry via `phaseVisibility`. Which phases an instrument is visible in is resolved centrally; use `isInstrumentVisible(def, phase)` and `getOrderedVisibleKeys(instruments, phase)`. Renderers consume visibility only and must not branch on phase (no phase literals in BaseCampLane or other renderers). Moving an instrument between phases requires only editing `phaseVisibility` in the registry. This invariant is enforced by INSTRUMENT-02.

### How to move an instrument between phases (runbook)

This project supports **modular movement of instruments between lifecycle phases**.  
To prevent regressions, there is **exactly one supported way** to do this.

### The only allowed edit surface

To add, remove, or move an instrument between phases:

1. Open the instrument registry (e.g. `src/app/lib/domain/instruments/registry.ts`)
2. Edit **only** the following fields on the instrument definition:
   - `phaseVisibility: CoordinationStatus[]`
   - `order: number`

Example:

```ts
{
  id: "flights",
  kind: "job",
  phaseVisibility: ["locked", "gameday"],
  order: 20,
}
```

### Anchor vs instrument

**Anchors** are non-composite. They display text, chevrons, open modals, or trigger navigation only. Anchors must not render instrument bodies or own expand/collapse state. The boundary is enforced by ANCHOR-01: anchor render components (e.g. `AnchorRow`) must not import `RenderBody`, `InlineInstrumentSection`, or `resolveInstrumentRenderState`, and must not declare state variables such as `expanded`, `isOpen`, or `isCollapsed`.

### Buttons and CTAs

- Use `btn-*` semantic classes for all CTAs (`btn-primary`, `btn-anticipation`, `btn-ghost`, `btn-danger`)
- Do not build CTAs with `bg-brand-*` / `text-*` utilities directly
- Green is for anticipation (`btn-anticipation`), not for general navigation
- Amber is reserved exclusively for mode transitions (Enter / Return GameDay)
- Do not add `text-white` alongside `btn-*` classes (foreground colours are included)

### Time picking (canonical)

The app uses a **single public time-picking component** and a Pixel-style clock-face UI. This is the canonical standard; do not introduce alternative pickers or native time inputs for core flows.

- **Canonical component:** `src/app/components/ui/TimePicker.tsx` — the only public entry point. All time selection in the app must use this component (props: `label`, `valueHHMM`, `onChangeHHMM`, `defaultPeriod`, `minuteStep`, `placeholder`).
- **Internal UI:** `src/app/components/ui/PixelTimePicker.tsx` — Pixel-inspired clock-face picker, light mode aligned to Day Fore It tokens. **Only** `TimePicker.tsx` may import `PixelTimePicker`; no other file may reference it.

**Rules:**

1. Do not introduce new time picker UIs (no ad-hoc dials, grids, or alternate components).
2. Do not use native `<input type="time">` for core flows.
3. All time selection must use the `TimePicker` component from `src/app/components/ui/TimePicker.tsx`.
4. AM/PM segmented control uses a soft container with a clearly visible selected translucent fill (anticipation tint); selected state must be obvious at a glance.
5. Hour selection advances automatically to minute selection; the hour tile returns to the hour stage; there is no separate “Back” button.

**Note:** This is a UI standard. Canonical storage remains 24h `"HH:MM"`; the picker exposes 12h + AM/PM for input only.

### Terminology: Flight vs Transport

- **Flight** is reserved for golf tee groupings (core domain). Used for GameDay scoring, tee groups, and trip_flights. Do not use for logistics or travel.
- **Transport** is the canonical logistics umbrella (air/ferry/transfer) for pre-game planning. Chroma shows **transport readiness** only ("Planned" when trip.logistics has itinerary/ferry details; else "—"). No narrative ferry text or operator names in chroma.

### Non-Negotiables

- No card stacks
- No action-first hierarchy
- No decorative UI
- No visual clutter disguised as functionality

Design decisions are judged by calm, clarity, and flow — not novelty.

## 4. BaseCamp Orchestration Model

### Purpose (v1)

BaseCamp is a **calm, truthful snapshot of trip readiness**. It is the organiser's coordination surface for a trip. It is not a dashboard, not a CRUD panel, and not a settings page. It is **not** a task board, workflow, or lane-based system. It is **not** a phase progression UI.

- BaseCamp renders the **minimum surface necessary** to reflect current reality. Nothing more.
- **Time does not advance the UI;** unmet dependencies do. Users should never feel like they are "managing a process."
- The product stance is: ambient, not interruptive; observational, not instructional; coordination-first, not configuration-first.
- **Full behavioural contract (render states, anchors vs instruments, allowed instruments, Floating, invariants):** [basecamp-v1.md](./basecamp-v1.md). That document is frozen v1 source of truth for BaseCamp behaviour.

### Mental Model (v1)

BaseCamp is a **readiness snapshot**, not a workflow rail. Phases exist in the domain but are **latent in the UI**. The user sees:

- **Anchors** — Always visible, read-only, status only. Each anchor is in exactly one state: Done / Floating / Blocked. See [basecamp-v1.md — Anchors vs Instruments](./basecamp-v1.md#c-anchors-vs-instruments).
- **At most one instrument** — Appears only when a blocking dependency exists. Disappears immediately when resolved. Instruments are rare, ephemeral, and singular. No lanes, no multi-task view, no phase completion UI.

BaseCamp may render with **zero instruments** and still be complete. Empty is valid. Calm is the default.

### Design Rules

- No card containers, no stacked forms, no duplicate control surfaces.
- No buttons unless action is rare and intentional.
- Defaults are strong; overrides exist but are de-emphasised.
- No lanes, no phase progression UI, no time-based prompts, no placeholder future steps. See [basecamp-v1.md — v1 Allowed Instruments](./basecamp-v1.md#d-v1-allowed-instruments-locked).

### Consequence

BaseCamp behaviour (what renders when, anchors vs instruments, allowed instruments) is defined in [basecamp-v1.md](./basecamp-v1.md). Implementation must not contradict that contract. Legacy UI that mimics task boards, workflows, or phase lanes must be removed or refactored to align.

### Architecture Direction — Domain-Oriented Orchestration

Day Fore It is migrating from:
- page-level UI logic
- duplicated business rules
- ad-hoc permission checks

to:
- domain-driven orchestration
- EventContext as the single DTO
- instruments as the single UI unit
- registry-driven rendering

Principles:
- lifecycle logic lives only in lifecycle engine
- permissions live only in policy
- rendering is registry-driven
- each capability has exactly one control surface

Legacy UI blocks must be migrated into instruments and deleted, not co-exist.

The long-term goal:
- Trip page becomes a composition shell
- BaseCamp becomes a pure orchestration rail
- scoring, results, logistics, and seasons become independent modules

## 5. Orchestration Architecture

Day Fore It is built around an orchestration model, not a dashboard model.

BaseCamp is not a settings page, not a CRUD surface, and not a form stack. It is a **readiness snapshot**: it shows the minimum surface necessary to reflect current reality. Time does not advance the UI; unmet dependencies do. At most one instrument is visible at a time; anchors are always visible (Done / Floating / Blocked). Full contract: [basecamp-v1.md](./basecamp-v1.md).

### Design stance
- Ambient, not interruptive  
- Observational, not instructional  
- Coordination-first, not configuration-first  
- Defaults over settings  
- Rare actions de-emphasised  

### Structural consequences
- All orchestration logic flows through EventContext (or equivalent domain state)
- BaseCamp render is governed by [basecamp-v1.md](./basecamp-v1.md): anchors + at most one instrument when blocked
- Each blocking dependency has at most one control surface (one instrument)
- No lanes, no phase progression UI, no multi-task view  

This architecture exists to:
- remove duplicated business logic  
- stabilise phase behaviour  
- allow UI, flow, and sequencing to evolve independently  

---

## Migration Strategy — Domain Orchestration

The product is migrating from:
- page-level orchestration  
- duplicated UI logic  
- ad-hoc permission checks  

to:
- EventContext as the single DTO  
- lifecycle engine as the single state source  
- domain instruments as the single UI unit  
- registry-driven rendering  

Rules:
- no legacy UI may coexist with a migrated instrument  
- migration deletes old blocks immediately  
- all sequencing logic lives outside components  

Long-term goal:
- Trip page becomes a composition shell  
- BaseCamp becomes a pure orchestration rail  
- scoring, logistics, results, seasons become independent modules

## GameDay Mode (Design v1 — Living Spec)

### Simple is hard (GameDay)

"Simple is hard" means GameDay succeeds if the golfer never has to think about the app. Performance is part of simplicity: instant render on unlock, no blocking auth or network for core interactions, no spinners for scoring.

If the app takes two seconds to load when a player unlocks their phone, the design has failed. Every interaction must feel inevitable and thoughtless.

---

### GameDay as a Distinct Mode

GameDay is a deliberate mode shift, not just another screen or theme variation.

GameDay represents "the day has started". It is visually, behaviorally, and emotionally distinct from the base app. Entering GameDay should feel like crossing a threshold. Exiting GameDay returns the user to the clean, calm coordination experience.

This intentional distinction prevents inconsistency and preserves coherence across the product.

---

### GameDay mode — intuitive instrument baseline (canonical)

"GameDay Mode (v1) — Final Locked Design" below. The frozen section is authoritative.

### Design Intent & Emotional Tone

GameDay must feel:
- calm
- warm
- expressive
- premium
- social
- confidence-boosting

GameDay must NOT feel:
- analytical
- instructional
- coachy
- cluttered
- admin-heavy
- competitive in a stressful way

Scoring exists to:
- record the day
- support handicaps
- enable light banter and memory

Scoring does NOT exist to optimise performance mid-round.

---

### Visual Language (Mode-Scoped Expression)

The base app remains clean, neutral, and restrained. GameDay allows richer colour, warmer tones, and stronger brand expression.

Non-negotiables:
- Expression is contained, not global
- One hero surface (the GameDay Hole Card) carries the majority of visual weight
- No visual shouting, no neon, no chaos
- GameDay styling is strictly scoped to the GameDay mode container and must not leak into other parts of the app

---

### Motion & Interaction Principles

Motion must be:
- restrained
- tactile
- intentional

Allowed:
- micro-interactions (press, compress, subtle rebound)
- short crossfades or slides for hole transitions
- quiet confirmation cues (e.g. save or sync feedback)

Explicitly banned:
- looping animations
- confetti or celebratory effects
- gamification visuals
- motion that delays interaction

Premium feel comes from responsiveness and restraint, not visual noise.

---

### One-Hand, Outdoor-First Constraint

GameDay must be fully usable with one hand. Primary actions must live within the thumb zone. Hit targets must be generous and forgiving. UI must tolerate bright sunlight, glare, and intermittent attention.

---

### Performance as a Design Requirement

Performance is part of design, not engineering.

GameDay must:
- render instantly from local state
- never block scoring on network or authentication
- tolerate patchy reception gracefully
- avoid spinners for core actions

If the app takes two seconds to load when a player unlocks their phone, the design has failed.

---

### Offline-First & Trust UX

All scoring actions commit locally first. Sync occurs quietly in the background.

Offline/sync must be invisible to the user. No user-visible offline state toggles.

Explicitly banned:
- scary or alarming offline error states
- forcing users to manage sync manually
- ambiguous save states

---

### Future GPS Compatibility (Design-Locked)

GPS is a future additive module, not core to scoring.

A permanent "Distance" panel slot exists in GameDay. v1 displays a "Coming soon" placeholder. v2 swaps internals without layout rebuild.

GPS must never delay GameDay first paint. GPS is visual and approximate, not authoritative.

---

### Non-Negotiable GameDay Rules (Summary)

- one primary action at a time
- instant usability on unlock
- mode-scoped branding only
- offline-first scoring
- expressive but calm visual language
- no coachy or judgemental language

## 6. Brand Contract

### Single Source of Truth

All UI colours are managed via CSS variables in **`src/app/globals.css`**.

### Core Semantic Tokens

- **Surfaces:** `--bg`, `--surface`, `--surface-2`, `--header-bg` (RGB space)
- **Text:** `--fg`, `--muted` (RGB space)
- **Borders & Rings:** `--border`, `--ring` (RGB space)

### Brand Semantic Tokens

- **Primary:** `--primary`, `--primary-fg` (RGB space) — primary actions (warm ink, not navy)
- **Anticipation:** `--anticipation`, `--anticipation-fg` (RGB space) — time-critical actions (green)
- **Danger:** `--danger`, `--danger-fg` (RGB space) — destructive actions
- **Warning:** `--warning`, `--warning-fg` (RGB space) — required markers / attention (amber)

### Semantic Button Classes

All CTAs must use semantic button classes (100% token-backed):
- `btn-primary` — primary actions (warm ink background, white text)
- `btn-anticipation` — time-critical actions (green background, white text)
- `btn-ghost` — quiet/secondary actions (transparent, bordered)
- `btn-danger` — destructive actions (red background, white text)

### Banned Patterns

**Never use:**
- `bg-brand-*` utilities (use `bg-anticipation` or `btn-anticipation` instead)
- `text-black`, `bg-white`, `bg-black` (use `text-fg`, `bg-surface`, etc.)
- Tailwind default palette (`bg-slate-*`, `text-gray-*`, etc.) — use semantic tokens
- Hex colours in JSX/TSX style attributes — use CSS variables
- `text-white` alongside `btn-*` classes (semantic buttons must not need glue)

### Enforcement

Run `npm run brand:audit` before deploying. This script scans `src/` for banned patterns and fails if any are found.

**brand:audit must pass before deploy.**

### Canonical Assets

- **`public/brand/logo-mark.png`** — Primary in-app logo mark
- **`src/app/icon.tsx`** — Browser favicon (via Next.js metadata)
- **`public/icon-192.png`** and **`public/icon-512.png`** — PWA manifest icons

Theme colour must be updated in both:
- `src/app/layout.tsx` (viewport metadata) — use `rgb(46, 143, 99)` format, not hex
- `public/manifest.json` (PWA manifest)

## 7. Core Flows

### Onboarding / Profile

- Profile completion is a soft prompt, never a gate
- Missing profile data does not block trip participation
- Bootstrap failures do not downgrade profile state (use `null`, not `false`)

### Members

- All authenticated users can see all members of their approved groups.
- Admin capabilities (approval, role management, member removal) are derived from per-group role only. There is no admin-mode toggle; when the user selects a group where they are admin, approval controls and pending list appear automatically.
- "All groups" is read-only. A "Review" banner appears when there is pending in any admin group; clicking it switches to that group so the user can act.

### Trips / Base Camp

- Base Camp is the organiser's operating surface on Group Trip Details
- Uses instruments (internal primitives) to keep UI calm and modular
- When an agent is attached to a trip, an **Agent Collaboration** lane appears in BaseCamp (read-mostly; see [Agent Collaboration](#agent-collaboration))
- Non-blocking: missing details never halt signups or phase progression
- No checklist UI, no progress bars, no "X of Y"

### Trips list (v1)

- **Single chronological list.** Group trips and hosted rounds are mixed by date (earliest first). One continuous canvas; no section headers.
- **Visual hierarchy:** Title, metadata line, optional prestige rail (group trips only), optional personal status pill ("Going").
- **Prestige:** Group trips use a subtle ceremonial **left rail** (amber, overlay-only). No "Group trip" badge or pill.
- **Personal status:** The only pill in the list row is the green **"Going"** pill (joined/confirmed). No other row-level badges.
- **Row action label (per-trip):** Trips list action verbs are per-trip and derived from membership role in the trip's group (not "admin anywhere"). Label semantics: admin = Manage, participant = Details. Destinations unchanged.

### Non-admin Trip Details (v1)

- **Participant-focused, read-only view.** No BaseCamp instruments. No full chroma snapshot.
- **Curated snapshot:** Participants see a subset of snapshot rows only (meet time, meeting point, course, format, transport). Admin-only data (spots, sign-ups, agent pack, etc.) is intentionally hidden from participants.
- **Narrative card:** Meeting (time + point), Transport details (generic, de-duplicated), Notes. No modality labels (no "Itinerary" / "Ferry" taxonomy in v1).

### Hosted Round Creation

- Lightweight, host-owned, no implied structure
- Meet details are the only coordination input
- No "publish / lock / logistics" steps
- Post-creation redirects directly to Trip Details (no intermediate success screen)

### GameDay

- GameDay is execution mode
- Scoring is live instrument mode
- No leaderboards mid-round
- Direct manipulation: tap, slide, swipe

#### Hardening invariants

- GameDay visibility: A member only sees or can resume a GameDay round if they are a confirmed attendee of the trip, or the trip organiser/creator. Otherwise, treat the round as not found (do not leak existence).
- GameDay expiry: A GameDay round auto-expires at 23:59 local time on the trip date. Local time is the timezone of the course/trip, not the user's device timezone. After expiry, the round is not considered active and "Resume GameDay" must not display; direct navigation behaves as not found.
- Calm failure surfaces: Never redirect by guessing routes. Invalid or unavailable rounds show a calm inline notice. APIs return consistent error envelopes.

### "No Success Screens" Rule

- No dead-end success pages
- No one-CTA confirmation screens
- Post-creation flows redirect directly to canonical destinations:
  - Created trip → `/trips/<tripId>`
  - Created hosted round → `/trips/<tripId>`
  - Joined group → `/members`
  - Created group → `/members`

## 8. Trip Lifecycle

### Canonical Phases (Group Trips)

1. **Forming** (before sign-ups open)
2. **Sign-ups open**
3. **Locked** (sign-ups closed → GameDay)
4. **GameDay**
5. **In play**
6. **Completed**

### Phase Gating Rule

Only instruments whose phase matches the current lifecycle phase may appear in BaseCamp.

Phases: `forming → signups_open → locked → gameday → in_play → completed`

### Canonical Moments

- **Sign-ups open moment:** `effectiveOpenMoment = trip.signups_opened_at ?? (trip.date - 30 days)`
- **Sign-ups close moment:** `effectiveCloseMoment = trip.cutoffAt ?? (trip.date - 4 days at 23:59 SGT)`
- **GameDay moment:** `gameDayMoment = trip.date`
- **In-play moment:** `inPlayMoment = scoringStarted === true`
- **Completed moment:** `completedMoment = resultsPublished === true`

### Phase Derivation Rules

1. `resultsPublished` → `"completed"` (irreversible)
2. `scoringStarted` → `"in_play"` (irreversible)
3. `isGameDay` (trip.date === today SGT) → `"gameday"`
4. `now >= signupCloseAtEffective` AND `today < trip.date` → `"locked"`
5. `now >= effectiveOpenMoment` AND `now < signupCloseAtEffective` → `"signups_open"`
6. else → `"forming"` (default)

### Lifecycle legacy quarantine

`draft` and `scheduled` are **legacy read-only** values. When read, the lifecycle engine WARNs and falls back safely (see lifecycle engine). **Write paths must never emit them.** Only canonical `coordination_status` values (`forming`, `signups_open`, `locked`, `gameday`, `in_play`, `completed`) may be written. This is enforced by LIFECYCLE-02.

### BaseCamp Instrument Set (v1) — Contract in basecamp-v1.md

**Authoritative behavioural contract:** [basecamp-v1.md](./basecamp-v1.md). The following is a domain/lifecycle reference only; **render behaviour** (when instruments appear, at most one at a time, anchors Done/Floating/Blocked) is defined there.

**v1 allowed instruments (locked):** Roster Lock, Booking (generic), Compliance / Passport Details, Tee Grouping, GameDay Activation. No other instruments in v1. No lanes, no phase completion UI, no multi-task views, no time-based prompts, no placeholder future steps. See [basecamp-v1.md — D. v1 Allowed Instruments](./basecamp-v1.md#d-v1-allowed-instruments-locked).

**Domain phases** (lifecycle engine; phases are latent in UI): forming, signups_open, locked, gameday, in_play, completed. Phase gating exists in the domain; BaseCamp **render** is dependency-driven (Day 1 → Day N compression). See [basecamp-v1.md — B. BaseCamp States](./basecamp-v1.md#b-basecamp-states-v1-render-contract).

**Legacy / scenario reference (deprecated for render logic):** Trip Name, Capacity, Sign-ups Window, Roster, Transport, Flights Editor, Export Docs, Meet Details, Enter GameDay, Publish Results — these names may still appear in domain or migration context, but **what the user sees** and **when** is governed by basecamp-v1.md (render states, at most one instrument, anchors only otherwise). Agent Coordination lane (when agent attached) remains; see [Agent Collaboration](#agent-collaboration).

### Base Camp Anchors (v1 semantics)

Anchors are **always visible**, **read-only**, **status only**. Each anchor must be in exactly one state: **Done** | **Floating** | **Blocked**. Anchors do not advance phases; they reflect truth. **Floating** = intentional uncertainty (not incomplete, not failure, no action required). Full semantics: [basecamp-v1.md — C. Anchors vs Instruments](./basecamp-v1.md#c-anchors-vs-instruments) and [E. Intentional Uncertainty](./basecamp-v1.md#e-intentional-uncertainty-floating).

**Domain-phase labels** (for chroma/narrative only; not the anchor state model): Forming, Sign-ups open, Locked, GameDay, In play, Completed. Actionable chevrons (e.g. "Open sign-ups now", "Close sign-ups now") remain organiser actions where applicable; they do not change the anchor contract (Done / Floating / Blocked).

### Instrument Completion Semantics (v1)

An instrument is considered DONE only after the organiser explicitly saves or confirms it inside BaseCamp.

Presence of default or prefilled values does NOT mark an instrument complete.

Each instrument owns a persistent confirmation flag stored on the trip record.

**Confirmation flags:**
- `trip_name` → `decisionLogistics.tripNameConfirmed`
- `capacity` → `logistics.capacityConfirmed`
- `signups_window` → `decisionLogistics.signupsWindowConfirmed`
- `roster` → `decisionLogistics.rosterConfirmed`
- `flights_plan` → `decisionLogistics.flightsConfirmed`
- `meet_details` → `logistics.meetConfirmed`
- `logistics` → `logistics.transportConfirmed`

**Rules:**
- DONE state depends only on these flags
- Values alone never imply completion
- DONE state must persist across sessions and devices

### Instrument Persistence Contract

All BaseCamp instrument state is persisted in JSON blobs on the trip record.

**JSON columns (authoritative):**
- `trips.decision_logistics` (jsonb) — Decision-grade logistics and confirmation flags
- `trips.logistics` (jsonb) — Operational logistics and confirmation flags

**Rules:**
- All instrument state must be persisted in these JSON columns
- DONE state must be derived only from JSON fields (confirmation flags)
- Flat trip columns (`meeting_point`, `meet_time`, `ferry_details`, `notes`, `capacity`) are legacy compatibility only
- Legacy columns must never overwrite existing JSON state
- UI state must never be authoritative; always hydrate from database JSON
- Hydration must prefer JSON and never overwrite it
- All new writes must go to jsonb columns only

**Deprecation:**
- Flat columns are deprecated for writes (read-only for backward compatibility)
- Future instruments must persist state into JSON blobs only

### Scenario-dependent Instruments

Some instruments appear only when the trip scenario includes specific requirements:

- **Transport** (logistics) appears only when scenario includes travel/logistics
- **Export Docs** appears only when scenario includes organiser booking or external agent. Deprecated as primary workflow; intended replacement is Attendees list with inline Travel docs plus Flights document (see [Agent Collaboration](#agent-collaboration)). Do not rely on "Export Docs" as the primary agent coordination surface.

All other instruments are scenario-invariant.

Scenario gating is applied in addition to phase gating. An instrument must satisfy both.

### BaseCamp UI Transition Rules (v1)

On successful save:
- instrument must immediately transition to DONE state
- collapse to compact row (compactWhenDone)
- update local state before any reload

No instrument may remain in editing state after successful save.

### Soft vs Hard Gating

- **Soft gates:** Missing details show prompts but do not block progression (e.g. meet details, travel outline). Meet-up details are contextual, editable early, and non-blocking. Transport (flights/ferries) is informational coordination only in v1; there is no hard transport gate. See [basecamp-v1.md — F. Meet-up & Transport Semantics](./basecamp-v1.md#f-meet-up--transport-semantics-v1).
- **Hard gates:** System-enforced boundaries (e.g. sign-ups close moment, GameDay moment) exist in the domain; BaseCamp render is dependency-driven (at most one instrument when blocked). See [basecamp-v1.md](./basecamp-v1.md).
- Instruments appear only when a blocking dependency exists; they disappear when resolved. No instrument for "progress" or "fill space."

### Sign-ups Gates

- `signups_opened_at` is one-way: set once during Forming phase, never cleared
- Default open: `trip.date - 30 days`
- Default close: `trip.date - 4 days at 23:59 SGT`
- Both can be overridden via Base Camp anchor actions (group admins only)

## Agent Collaboration

Agent Collaboration exists to replace external spreadsheets and messaging loops by providing a single, persistent in-product coordination surface. Coordination first: agents primarily monitor progress and act on organiser decisions and system signals; they also work progressively as members complete Travel docs. Language is plain and in-product: Attendees, Flights document, Travel docs, Clarifications, Signals. No logistics-heavy nouns (manifest, ticketing console, operations dashboard).

### Personas

- **Organiser:** Group admin who owns the trip. Sees BaseCamp and can attach/detach agents, manage Attendees, generate Flights document, and use Clarifications.
- **Agent:** External collaborator with trip-scoped access only. Sees an Agent View projection (same app, separate boundary); no BaseCamp access. Reacts to signals and uses Attendees (with inline Travel docs), Flights document, and Clarifications.
- **Member:** Participant. Sees Trip Details and member-facing instruments only; no BaseCamp, no Agent View.

### Information architecture

- BaseCamp remains the organiser home and is visible to group admins only. See [4. BaseCamp Orchestration Model](#4-basecamp-orchestration-model) and [8. Trip Lifecycle](#8-trip-lifecycle).
- The **Agent Coordination lane** appears inside BaseCamp as a persistent lane when an agent is attached. It mirrors Agent View content (signals, Clarifications, attendee travel-docs state). Organiser replies and resolves Clarifications here. Lane may collapse but remains always accessible. No navigation away from BaseCamp required. See [Agent Coordination lane (BaseCamp)](#agent-coordination-lane-basecamp).
- Agents do NOT see BaseCamp. Agents access the same coordination reality via an **Agent View** — a trip-level projection within the same app shell, with a separate boundary from member/admin surfaces. The agent surface is not a separate product. See [Agent View — Placement & navigation](#agent-view--placement--navigation) and [Agent View — Page structure](#agent-view--page-structure-top-to-bottom).
- Members continue not to see BaseCamp; members interact through their existing instruments and projections. Members do not see agent coordination. See [Role-based visibility: trip details (basecamp)](#role-based-visibility-trip-details-basecamp).

### Access model (capability-by-relationship)

- Group roles remain per-group only; no global admin semantics. See [Admin Mode](#admin-mode) and [Members](#members).
- Do NOT add an "agent role" to the role engine. **Agent** is a **trip-scoped capability relationship** granted by a group admin: a user can be a normal user everywhere (create groups, join trips, etc.) and separately can be attached as an agent to a specific trip (trip-scoped agent attachment).
- Who can attach/detach: organiser (group admin) only, from BaseCamp. Revocation is immediate and deterministic; removing attachment removes all agent visibility for that trip.
- All agent access is attributable to an authenticated user and is revocable.

### Add Agent flow (invite + directory)

- In BaseCamp, organiser action: **Add Agent**.
- Two paths:
  - **Invite by email/phone (on-ramp):** Agent receives an invite that leads to sign-in/sign-up, then lands directly in the trip’s Agent View.
  - **Pick from directory (fast path):** Organiser selects an existing user who is already discoverable as an agent collaborator. Directory is a discovery layer, not a permission grant. Directory listing should prioritise recent agents used by this group/organiser (avoid "pick from hundreds").
- Avoid "role self-declaration" language; use "directory opt-in / discoverability".

### Agent View — Placement & navigation

- **Agent View** is a trip-level projection available to authenticated users with trip-scoped agent access. It lives inside the same app shell; not a separate product.
- **Entry point:** Trips list → trip row label **"Coordinating"** (or equivalent) for trips where the user is an attached agent. Selecting the trip opens the Agent View for that trip. No mode switches; same trip, different projection.
- Agents never see BaseCamp. Agents never see member-facing Trip Details as organisers do.

### Agent View — Page structure (top to bottom)

Single-scroll vertical layout. Order is fixed.

**A) Trip header (context only)**  
- Trip name, dates, location. Calm, non-interactive. No controls, no phase chrome.

**B) Signals strip**  
- Read-only chips: roster status, confirmation counts, travel docs completion (e.g. X/Y complete), flights status. Signals inform confidence and sequencing; they do not gate visibility. No interactive controls in the strip.

**C) Attendees (primary working surface)**  
- Canonical coordination list. Inline Travel docs for international trips with external agent. Progressive visibility as attendees complete fields. Expanded rows (no modals) reveal raw passport fields. See [Attendees — Design behaviour](#attendees--design-behaviour).

**D) Flights document**  
- Appears once generated. View / Download actions. Secondary prominence; does not dominate the scroll.

**E) Clarifications**  
- Structured coordination instrument (not chat). See [Clarifications — Instrument design](#clarifications--instrument-design).

### Attendees as the canonical coordination surface

- The **Attendees** list is the single canonical roster surface for coordination. See [BaseCamp Instrument Set (v1)](#basecamp-instrument-set-v1) (Roster).
- For international trips with an external agent attached, the Attendees list includes **Travel docs** inline; it is not a separate file or screen for the agent. Travel docs completion is visible per attendee as "Complete / Incomplete" plus missing-field tags. As soon as an attendee completes required fields, the agent can see the raw fields inline (immediately; no waiting for roster lock).
- **Required Travel docs fields (v1):** passport name, passport number, nationality, issue date, expiry date. No passport photos in the product.
- The intended replacement for legacy "Export Docs" as primary workflow is: Attendees list with inline Travel docs plus Flights document. Downloads exist only as convenience.

### Attendees — Design behaviour

- Attendees list is the single canonical roster surface for agents. Always visible per row: name, status, travel docs completeness, missing-field tags.
- **Expanded inline section** (per row, no modal): reveals passport name, passport number, nationality, issue date, expiry date when available. Expansion is inline; no overlay or dialog.
- Recently updated rows may use subtle highlight (e.g. brief emphasis) to draw attention without reshuffling. Sorting favours clarity but avoids aggressive reshuffling on every update.
- No agent edit controls. Agent has read-only visibility; organiser and attendees own mutations.

### Flights document

- Flights generation produces a **Flights document** that the agent can view/download and use downstream (e.g. sending to club for carts). This replaces ad-hoc exports as the primary workflow; downloads are secondary convenience actions. Naming: "Flights document" (not "manifest", not "pack"). See [Terminology: Flight vs Transport](#terminology-flight-vs-transport) — Flight is reserved for golf tee groupings; the Flights document is the output artefact for coordination.

### Signals (read-only coordination beacons)

- **Signals** are read-only state beacons that agents react to. They inform confidence and sequencing, not permission. No new lifecycle states are introduced. Examples (derived from canonical state and/or system outputs): roster locked (or existing equivalent), flights generated/updated, travel docs completion progress (X/Y complete). These are projections; they do not introduce new lifecycle semantics.

### Clarifications — Instrument design

- **Clarifications** are discrete items, not free-form chat. Each clarification has: author, prompt, replies (one level deep), status (Open / Resolved).
- Both agent and organiser may post clarifications. Either party may mark a clarification Resolved. Resolved items collapse by default. Follow-up questions create **new** clarification items (no nested threads).
- System-generated events (e.g. "Roster locked", "Flights generated") may appear as passive entries in the same surface; they do not have replies or resolution. Tone: short, factual, operational. Append-only; no edits/deletes. Auditable; do not mutate trip meaning. Intended to reduce reliance on external messaging while keeping everything inside the product.

### Security and hardening invariants

- Agent collaboration is trip-scoped; no group-wide admin capabilities are implied.
- Travel docs fields are sensitive. Only the attendee (self), group admins (organisers), and the attached agent for that trip can access raw fields. Travel docs fields must be encrypted at rest (implementation deferred; requirement is explicit). No passport photos.
- All agent access is attributable to an authenticated user and is revocable.
- Clarifications are append-only, auditable, and do not mutate trip meaning.
- No lifecycle changes and no new phases/states introduced by this feature.

### Agent Coordination lane (BaseCamp)

- Lives inside BaseCamp as a **persistent lane** visible to group admins once an agent is attached. Mirrors Agent View content: signals, Clarifications, attendee travel-docs state (read-only). Organiser replies and resolves Clarifications here. No navigation away from BaseCamp required. Lane may collapse but remains always accessible. Same coordination reality as Agent View; two projections, one source. See [basecamp-layout.md](../basecamp-layout.md) for lane contract.

### Design principles (Agent Collaboration)

- **Coordination over control** — Surfaces inform and align; they do not gate or approve.
- **Signals over messages** — Read-only beacons carry confidence and sequencing; Clarifications carry discrete questions and resolutions.
- **Inline visibility over exports** — Attendees with inline Travel docs is canonical; downloads are convenience only.
- **Resolution over endless discussion** — Clarifications are discrete items with Open/Resolved; follow-ups create new items.
- **Projection over mutation** — Agent View is read-only; organiser mutates from BaseCamp. Two projections of the same coordination reality.

### Non-goals (out-of-scope)

- No approval workflow gates for agent visibility.
- No "export docs" as the primary workflow; primary is Attendees with inline Travel docs + Flights document; downloads are convenience only.
- No agent powers to change trip state (no roster edits, no lifecycle actions).
- No member access to BaseCamp.
- No new group roles.

### Design non-goals (explicit)

- No chat UX. Clarifications are structured items, not a chat thread.
- No approvals. Signals inform; they do not gate.
- No modal-heavy flows. Expanded rows and inline sections only; no overlay dialogs for Attendees or Clarifications.
- No separate "agent console" or "operations dashboard". Agent View is a projection within the same app.
- No member visibility into agent coordination. Members do not see Clarifications or agent-facing content.
- No duplication of BaseCamp instruments. Agent Coordination lane mirrors Agent View; it does not replicate Roster, Flights Editor, or other organiser instruments.

## 11. Role-Based Editing and Meet Details Prompts

### Banners Are Action-Only

Banners are reserved for actions the current user can take. Banners must never be used for FYI or informational messages only.

### Home Page Behavior

If meet details are missing and the user cannot edit them, show only inline muted microcopy inside the "You're playing today" instrument. No banner, no InlineNotice, no card. The status appears as two muted text lines within the orientation block.

### Meet details — Home behaviour

**Intent**

Banners on Home are action-only. Informational (FYI) states must never appear as banners. The primary "You're playing today" instrument owns all round-status context.

**Member experience**

Members never see a "Meet details needed" banner. Members never see any CTA related to meet details. If meet details are missing, members see a single, muted FYI line inside the "You're playing today" instrument:

Copy: "Meet details being confirmed."

This FYI must not appear outside the instrument (no banners, no top chrome, no notices).

**Host / admin experience**

Actionable banners ("Meet details needed" with CTA) are shown only when the user can edit meet details. Banners exist solely to prompt an action and must never be used for FYI.

**Ownership rules (explicit)**

**Hosted rounds** (`tripOrigin === 'member'`):
- Only the host can edit trip details and meet details.

**Group trips** (`tripOrigin === 'group'`):
- Only group admins for that group can edit trip details and meet details.

Editing meet details is disabled once scoring has started.

**Guardrails**

Do not introduce additional Home-level notices for meet details. Any future changes must respect: banners = actions, instruments = context.

### Editing Ownership

**Hosted rounds** (`tripOrigin === 'member'`):
- Host-only (creator/organiser can edit meet details)
- Authorization check: `trip.createdByMemberId === currentMemberId`

**Group rounds** (`tripOrigin === 'group'`):
- Group-admin-only
- Authorization check: user must be an admin of the trip's group

### Meet Details Editing Constraints

Editing stops once scoring has started. The `/trips/:id?edit=meet` deep link opens the editor only if:
- User is authorised (host for hosted rounds, group admin for group rounds), AND
- Scoring has not started

Non-authorised users who land on `/trips/:id?edit=meet` have the query parameter stripped and never see the editor.

### Row-Level Security Principles

- Avoid recursive policies (use SECURITY DEFINER helper functions for membership checks)
- Group-scoped access: approved members can read group data

## 11. Authentication (v1)

Day Fore It authentication is designed to be calm, familiar, and set-and-forget.

**Supported sign-in methods**
- Google OAuth
- Facebook OAuth
- Email and password

Apple Sign In is intentionally deferred due to setup complexity and lower marginal value.

**Explicitly not supported**
- Passwordless email / magic links
- SMS or phone-based authentication

**Email and password behaviour**
- New users may create an account with email and password.
- Email confirmation is required before first sign-in.
- If an account already exists for an email (e.g. via OAuth), the user is guided to continue with the appropriate provider.
- Password reset is handled via email using a dedicated reset flow.

**Password reset**
- Initiated from the sign-in page ("Forgot password?").
- Users are sent a secure reset link.
- Reset is completed on a dedicated route (`/reset-password`).
- Expired or invalid links show a calm inline warning with guidance to retry.

**Change password**
- Available only to users authenticated via email and password.
- Appears under Me → Security.
- Hidden entirely for OAuth-only sessions (Google / Facebook).
- Implemented as an inline expander, not a modal.

**Account linking**
- OAuth providers may link automatically to an existing user when emails match.
- Manual account linking is intentionally out of scope for v1.

### Role-based visibility: trip details (basecamp)

Day Fore It trips distinguish three roles for trip visibility and editing:

**Roles**
- **Member:** Read-only access to trip information. Cannot see organiser instruments, jobs, or phase controls.
- **Host (organiser):** Creator of the trip. Can edit trip details, manage attendees, control phases, and access all organiser instruments.
- **Admin:** Group-level administrator (in-app tools). Can edit group trips but not hosted rounds.

**Agent (trip-scoped capability, not a role)**  
- **Agent** is a trip-scoped capability relationship, not a group role. A user can be attached as an agent to a specific trip by the organiser (group admin). Agents see an **Agent View** projection (Attendees with inline Travel docs, Flights document, Clarifications, Signals); they do not see BaseCamp and cannot change trip state. See [Agent Collaboration](#agent-collaboration).

**Members and trip visibility**
- Members see trip information only.
- Members do not see organiser instruments, jobs, or phase controls.
- Members cannot access trip editing or coordination surfaces.

**Meet details banner contract**
- **Host:** Actionable "Meet details needed" banner with CTA link is shown only if:
  - Meet details are missing, and
  - Scoring has not started (trip is not in play).
- **Member:** If meet details are missing, members see at most an info-only notice with:
  - **Title:** "Meet details being confirmed"
  - **Body:** "Meet details haven't been added yet. Check back later."
- **Both:** If meet details exist, no banner or notice is shown.

**Deep link contract: `/trips/:id?edit=meet`**
- **Host:** If `canEditMeetDetails(...)` returns true, the editor opens and scrolls to the meet details section.
- **Non-host:** The `edit=meet` query parameter is stripped from the URL, the editor never opens, and an info-only notice is displayed.

**Mutation boundaries (v1 lock)**
- All trip mutations occur only via BaseCamp instruments. Member-facing Trip Details and Trips list are read-only projections.
- Zone C / experimental instruments that perform direct DB writes (e.g. TravelInstrument) are intentionally disabled in v1 and must not be enabled without a formal architecture decision.
- **Watchers/events** (trip_events, clubhouse_events) are read-only instrumentation; they do not create new mutation boundaries. Client logging must not block UI; insert-only, no SELECT for anon.

# GameDay Mode (v1) — Final Locked Design

This section locks the GameDay Mode v1 design, UX, behaviour, and guardrails as implemented in the GameDay sandbox prototype. This is the frozen v1 specification.

---

## 1. Core positioning (non-negotiable)

GameDay is:
- a distinct, premium "mode"
- calm, social, confidence-boosting
- built for one-hand use and intermittent attention

GameDay is NOT:
- coachy
- stat-heavy
- naggy
- admin-y

**"Simple is hard" is the guiding principle.** Every interaction must feel inevitable and thoughtless. Performance and responsiveness are part of simplicity. Instant is better than clever.

---

## 2. Screen structure (locked)

GameDay has two persistent regions:

### Top 2/3 — Play Canvas (v1 now, GPS-ready later)

Contains the hole context and navigation cues.

**Header:**
- "Thru hole X" (top left, muted microcopy)
- "Exit GameDay" (top right, accent-coloured action)

**Hole navigation:**
- Subtle "← previous hole" and "next hole →" affordances on the same canvas (not floating above it)
- Gesture-only navigation via edge rails (left rail: previous, right rail: next)

**Hole context:**
- Course name ("Tanah Merah") as a calm context line above the hole number (not as the header title)
- Hole number as the hero (large, left-aligned, weight 500)
- Par / Length / HCP as secondary rows beneath the hole number

**Shot entitlement (v1 intent, v2 implementation):**
- Beneath HCP, show: "You get one shot on this hole" / "You get two shots on this hole" / "You don't get a shot on this hole"
- Note: UX intent only; maths is internal

### Brand signature seam

A calm "DAY FORE IT" wordmark appears centered between the top canvas and bottom deck.

- Text-only (no icon), Inter, tracked (letter-spacing ~0.45em), weight 600
- Uses logo wordmark green (`#2e8f63` — brand anticipation green)
- This is a signature, not UI: never clickable, never repeated elsewhere

### Bottom 1/3 — Instrument Deck (state-driven)

The bottom third is a stateful deck with two modes:
- **InPlay state** (default)
- **Scoring state** (gesture matrix)

---

## 3. Instrument deck — InPlay state (default)

**Layout (two-row grid):**

**Row 1 — Two-column info:**
- **Left column (62%):** Leaderboard panel
  - Toggle: Flight / Group (segmented control, small)
  - Group leaderboard shows top 6 (design intent)
  - Scores displayed as nett relative to par/handicap context (e.g. -1, E, +3)
  - Typography slightly enlarged for sunlight readability (15px, line-height 1.4), still secondary to "Your score"
- **Right column (38%):** "Your score" tile
  - Large single value (E, -1, +2 etc.) — 56px font, weight 500
  - Top-aligned with leaderboard first row (via padding-top match)
  - Label "Your score" beneath, centered, 17px font (slightly higher emphasis than muted labels, no bold)
  - Semantic colour rule for the score:
    - stays ink (black/charcoal) at +1 and above
    - goes subtly green (`#2f7d5a`) at -1 and -2
    - becomes more green (`#1f6f4a`) at -3 or better
    - no red, no shame colour

**Row 2 — Full-width action rail:**
- Idle text: "Score hole →"
- Positioned in the LEFT THIRD of the rail, left-aligned within that third
- Uses the same Day Fore It green as the wordmark (`#2e8f63` — brand anticipation green)
- No button chrome: this is an action rail, not a button
- Full-width clickable area within the left third

## 4. Instrument deck — Scoring state (gesture matrix)

The scoring deck is a distinct sub-mode within the bottom third.

**Entry:**
- Tapping "Score hole →" switches the bottom third into Scoring state.
- There is no intermediate confirm-only state in InPlay.

**Layout:**
- **Player list on left** (vertical)
  - All players shown, active player highlighted
  - Sticky score badges: per-player score badges persist visibly as you move between players (draft vs committed states)
- **Horizontal score scrubber** (values left/right, selected centered and prominent)
  - Score dial shows 5 values centered around current strokes
  - Horizontal drag gesture adjusts score (drag RIGHT decreases, drag LEFT increases)
  - Snap rules: score selection snaps; must not feel like a free carousel

**Inertia hierarchy:**
- Selected row + selected value = most prominent (Tier A)
- Selected row + unselected values = muted + slightly smaller (Tier B)
- Unselected rows = most muted + smallest (Tier C; player names only, no score numbers)

**No looping:**
- Vertical player navigation cannot wrap from last player to first
- Player selection clamps at boundaries (Math.max(0, Math.min(players.length - 1, candidateIndex)))

**Snap rules:**
- Player selection snaps (vertical gesture, 48px threshold per step)
- Score selection snaps (horizontal gesture, 34px threshold per step)
- Must not feel like a free carousel

**Sticky scoring requirement:**
- Each player's last selected score persists visibly as you move between players.
- If the default score is already correct, the player must still be considered "scored" without requiring the user to move off and back.

**Scoring notation:**
- Score visual treatments are allowed (e.g. circles for birdie, squares for bogey) but only if they do not add clutter.
- Currently implemented in sandbox: shape decorators on selected score (Tier A only) based on relation to par:
  - diff <= -1: circle outline (birdie or better)
  - diff == +1: square outline (bogey)
  - diff == +2: double square outline (double bogey)

## 5. Commit flow (one deliberate action)

## 8. GameDay Architecture

GameDay scoring is flight-bounded: each flight (from `trip_flights`) maintains its own round state. The club sheet serves as the truth anchor: committed holes are locked and used for leaderboard calculations. Per-flight commits allow staggered starts (shotgun/tee times) while maintaining data integrity.

**Core Principles:**
- **Flight-bounded scoring**: Each flight has independent round state (`gameday_flight_rounds`). Participants belong to a flight via `trip_flight_slots`.
- **Club-sheet truth anchor**: Once a hole is committed per-flight (`gameday_hole_commits` with `flight_id`), scores become read-only and feed leaderboard calculations.
- **Per-flight commits**: Holes can be committed independently per flight, enabling staggered starts without cross-flight conflicts.
- **Derived nett/stableford**: Leaderboard calculations derive nett scores and stableford points from committed holes only. Gross strokes from `gameday_scores` are the source of truth.
- **Handicap has 3 states**: Declared Starter / Declared Established / Day Fore It Official (future).
- **Offline invisible**: All sync happens in the background (IndexedDB + WAL). No "offline" indicators. Users never wait for network.
- **Instant wake**: Round state loads from IndexedDB immediately (<100ms). Background sync refreshes data invisibly.

**Data Model:**
- `gameday_flight_rounds` — Per-flight round state (state, current_hole_index)
- `gameday_scores` — Score entries (trip_id, member_id, hole_number, strokes)
- `gameday_hole_commits` — Per-flight hole locks (trip_id, flight_id, hole_number)
- `gameday_round_participants` — Denormalised participant metadata for fast lookups

See [GameDay Architecture](./gameday-architecture.md) for complete specification.
